TallyBee is a tap counter that runs in the browser, hosted on GitHub Pages at tallybee.beeminder.com. It sends the tally to a Beeminder goal as a datapoint. The design goal is to match or beat ("Pareto-dominate") the tally counter in Beedroid, Beeminder's Android app.

How script.js works

  • Saved state: all of it lives under one localStorage key, tallybee: {count, requestid, pin, comment, prev, slug, folded}. It's checked by valid() on every load and every write.
  • Updates: every change goes through update(f), which loads, applies f, saves and re-renders. change(keys, f) also records prev so UNDO can reverse the last action (one level only).
  • No duplicate datapoints: requestid is Beeminder's idempotency key, so a resend after a lost reply updates the datapoint in place instead of adding another. A new one starts after each successful Submit and each Clear.
  • Odometer goals: these are goals that aren't cumulative ("kyoom" in Beeminder's terms), where each datapoint is a running total. The value sent is the count plus a base, the value of the datapoint added last. pin freezes that base on the first send so a resend is the same datapoint.
  • Multiple windows: windows coordinate through the Web Locks API (enqueue, exclusive for sends, shared for goal loads, Clear and UNDO) and through storage events.
  • Goal updates: while Beeminder is updating a goal (queued), the app reloads the goals every 2 s.
  • Per-goal links and icons: ?goal=slug selects a goal. The page builds its app manifest on the fly for that goal, so a home-screen icon made from the page opens that goal.

How beeminder.js works

  • Login is OAuth that hands back the token directly in the redirect URL. A per-tab state value stops crafted login links from logging you in as someone else.
  • The token is kept in localStorage under beeminder-token.
  • Every API call gives up after 30 s.
  • On a 401, the app forgets the token only if it's still the same one that was rejected, so it doesn't log out a newer login.
