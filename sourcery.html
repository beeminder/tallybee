TallyBee is a tap counter that runs in the browser, hosted on GitHub Pages at tallybee.beeminder.com. It sends the tally to a Beeminder goal as a datapoint. The design goal is to match or beat ("Pareto-dominate") the tally counter in Beedroid, Beeminder's Android app.

How script.js works

  • Saved state: all of it lives under one localStorage key, tallybee: {count, requestid, pin, comment, prev, slug, folded}. It's checked by valid() on every load and every write.
  • Updates: every change goes through update(f), which loads, applies f, saves and re-renders. change(keys, f) also records prev so UNDO can reverse the last action (one level only).
  • No duplicate datapoints: requestid is Beeminder's idempotency key, so a resend after a lost reply updates the datapoint in place instead of adding another. A new one starts after each successful Submit and each Clear.
  • Odometer goals: these are goals that aren't cumulative ("kyoom" in Beeminder's terms), where each datapoint is a running total. The value sent is the count plus a base, the value of the datapoint added last. pin freezes that base on the first send so a resend is the same datapoint.
  • Multiple windows: windows coordinate through the Web Locks API (enqueue, exclusive for sends, shared for goal loads, Clear and UNDO) and through storage events.
  • Goal updates: while Beeminder is updating a goal (queued), the app reloads the goals every 2 s.
  • Per-goal links and icons: ?goal=slug selects a goal. The page builds its app manifest on the fly for that goal, so a home-screen icon made from the page opens that goal.

How beeminder.js works

  • Login is OAuth that hands back the token directly in the redirect URL. A per-tab state value stops crafted login links from logging you in as someone else.
  • The token is kept in localStorage under beeminder-token.
  • Every API call gives up after 30 s.
  • On a 401, the app forgets the token only if it's still the same one that was rejected, so it doesn't log out a newer login.

how do ios home screen icons work?

Here's how they work as of iOS 26, and what that means for TallyBee. Nothing below has been tried on a real iPhone.

Making one. In Safari, Share → Add to Home Screen. Since iOS 16.4, other iPhone browsers can do it too. The sheet lets you edit the name. TallyBee's name defaults to the goal's name, like "pushups", from the app manifest it makes for each goal. The icon comes from the manifest's icons, or from the apple-touch-icon link.

Two kinds of icon. Since iOS 26, the sheet has an "Open as Web App" switch, on by default for every site.

  • On (a web app): it opens full screen in a window of its own, with no Safari bars, and shows as a separate app in the app switcher. It keeps its own storage, apart from Safari's: its own cookies, localStorage and service worker. Apple has treated this as by design since at least 2018.
  • Off (a bookmark): it opens in a normal Safari tab and shares Safari's storage.

Which page it opens. Sources disagree on whether iOS opens the page you were on or the manifest's start_url, and I found nothing authoritative from Apple. TallyBee makes both the same goal URL (like ?goal=pushups), so either way the icon should open that goal.

What that means for TallyBee:

  1. A per-goal icon should work: open the goal's page in Safari, then Add to Home Screen.
  2. Logins (web-app icons): an icon with its own storage needs its own login. Beeminder keeps one login token per app, so logging in from one icon logs TallyBee out in Safari and on your other devices. Dreev's agent says it also logs out the other icons (N15). That assumes each icon has storage separate from every other icon, not just from Safari. Apple only documents the separation from Safari, so this should be tested on a phone.
  3. Turning "Open as Web App" off avoids the separate logins: the icons share Safari's login. The cost is opening in a Safari tab instead of full screen.
  4. The count: if web-app icons each have their own storage, each has its own count. That's different from Android, and from bookmark icons, where every icon shares one count. That shared count is the problem dreev's question N8 describes.

Menus like this one usually open as a small box attached to the button that opens them. The sheet TallyBee shows now, sliding up from the bottom after a tap at the top, is the less common pattern. Two smaller findings: ☰ conventionally means something else, and a menu this short is often not worth hiding.

What the platforms do

  1. ☰ usually means navigation, at the top left, opening a drawer from the side. Android's docs describe the navigation drawer as "a slide-in menu that lets users navigate to various sections of your app. … Users can activate it by swiping from the side or tapping a menu icon." Their example puts that icon in the top bar's navigation slot, which is the left-hand one.
  2. A top-right button for less-used actions opens a small menu attached to it.
  • On Android this is the ⋮ overflow button: "A popup menu displays a vertical list of items that's anchored to the view that invokes the menu. … It appears below the anchor view if there is room, or above the view otherwise." Their example is Gmail's overflow button at the top right.
  • On iOS it's the … "More" button: "Consider using a More pull-down button to present items that don't need prominent positions in the main interface." Apple's text doesn't say where the menu opens. On iPhones it grows out of the button, but that's from familiarity with iOS, not from the HIG.
  1. A bottom sheet used as a menu is a real pattern on phones.
  • Material: "Modal bottom sheets are used as an alternative to inline menus or simple dialogs on mobile, especially when offering a long list of action items, or when items require longer descriptions and icons."
  • No source covered a sheet opened by a button at the top of the screen.
  • Apple's bottom-up action sheets are explicitly not menus: "Use an action sheet — not a menu — to provide choices related to an action. … people expect a menu to appear when they choose to reveal it."

  • Nielsen Norman Group (2016, 179 participants) found hidden navigation caused "a more than 20% drop in discoverability." On phones with 4 or fewer top-level links, they recommend showing them.

what actually goes wrong if a window takes another's count as it is?
03:46 Claude Code claude-opus-5-5 (xhigh) thought for 30s

Taps get lost without any error. The second window has the same pending datapoint, including its requestid, Beeminder's resend key. Beeminder's API docs say a datapoint sent with an existing requestid "will be updated" if it differs, and "will be ignored (the API will return "duplicate datapoint")" if it's identical.

For example, window A has 10 pushups pending and window B opens with a copy of that 10:

  1. Only one window adds taps: A taps 2 more and submits 12, then B submits its 10. Beeminder overwrites A's 12 with 10, so the 2 are lost. Both windows say "✓ Submission successful". In the reverse order (B submits first), Beeminder ends up right, because 12 includes B's 10.
  2. Both windows add taps: A taps 5 (15), B taps 2 (12), and both submit. Whichever goes second overwrites the first. Beeminder ends up with 12 or 15 instead of 17, again with both windows reporting success.
  3. Neither adds taps: A submits 10, then B submits its identical 10. Beeminder ignores the copy and answers "duplicate datapoint". B shows that as an error and keeps its 10 until you press Clear. Nothing on Beeminder is wrong.
  4. B is on another goal: Beeminder only matches resend keys within a goal. If B is on situps, the copied 10 goes in as 10 situps nobody did.

Even with nothing sent, B opening with A's count looks like the old shared count. But taps no longer show up in the other window.

Giving the copy its own resend key wouldn't fix it: case 1 would then send the 10 twice, so the count is inflated instead of lost.

So it only goes wrong if both windows submit a copied count, and when it does, the total on Beeminder is wrong while both windows say it worked. I'd keep the open-window check: it's already built and costs about 6 lines and a few milliseconds at startup.

how do we get the requestid? can a new tab just make a new one?
03:48 Claude Code claude-opus-5-5 (xhigh) thought for 15s

TallyBee makes the requestid itself, as a random UUID (crypto.randomUUID() in fresh() in script.js). It makes a new one after every successful Submit, on every Clear, and for a window that starts at 0. Beeminder only stores it; its API docs describe it as a string the app chooses "to uniquely identify this datapoint (scoped to this goal)".

So a new tab can make its own, and a tab starting at 0 already does. The catch is a tab that takes over a saved count. If it gives that count a new requestid, two things go wrong:

  • The other window is still open: both windows now hold the same taps under different keys. If both submit, Beeminder adds them twice: 10 pushups become 20.
  • The other window was closed: this is your close-and-reopen case. Say you pressed Submit and the reply got lost on a bad signal, but Beeminder got the datapoint. The count stays 10, waiting to be resent. Reopened with the same requestid, the resend updates that datapoint in place. With a new one, Beeminder adds a second 10.

So a count that's taken over has to keep its requestid, or a resend after a lost reply sends the count twice. That leaves the open-window check as the only thing stopping two open windows from sharing one.
